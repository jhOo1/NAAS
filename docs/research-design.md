# 方向 B · Task-Dependency-Aware Active Sensing

## 原案和研究判断

[指定对话最后一轮](https://chatgpt.com/c/6afd60fd-dfc8-83ec-a099-939aeaa60eeb)提出用机器人主动感知、事件触发与自触发控制，解决个人助理在长期任务中的多源观察调度。首版 training-free，由冻结 LLM 提取依赖和判断语义，确定性模块负责预算、排序、去重和调度。原案包含依赖提取、查询价值排序与适应性回查三个机制，并提出先做 SentinelBench，再做 VibeLifeBench。

论文最值得验证的缺口是**读取对多个任务的边际决策价值**。例如，一次航班核验有机会同时改变是否调整行程和是否改订接送。如果接送独立由会务方安排，同一条航班变化只影响行程，优先级应随之下降。两种情况可以保持查询成本、可见提示、变化风险和截止时间相同，按任务依赖构造最小配对。只展示自适应轮询优于固定轮询，能支持系统改进，方法贡献要通过与自适应且能切换来源的基线比较来验证。

## 方法

1. **提取依赖。** 从已见任务和工具返回提取 `待定决策 → 可改变该决策的事实 → 可读来源`。事实包含实体、条件、证据出处和有效期。决策记录行动分歧与最晚有用时刻。用工具清单验证来源，用已见文本追溯依赖。对同一后果去重，避免把一次计划修订和它的通知计成两个收益。
2. **生成可执行的观察。** 候选包括在可见页面注册等待、定时读取指定来源、读取后按结果核验详情。每项记录费用、完成时延、可能结果和所能影响的决策。只有正常观察到的页面变化能触发即时检查。静默来源只依据已知风险、截止时间与历史观察安排回查。
3. **对比现在查和等待。** 对所有策略提供同样的低成本信号和时钟。以最佳的低成本等待或直接行动作为参照，估计候选在完成时刻改变下游决定的期望收益，再扣去观察成本。先实现单步决策价值。若一个结果同时澄清多个待定决定，更新后再为候选重算边际收益。只有结构上相邻且单次读数可能缺乏决策价值的组合才进入两步诊断，例如列表提示和正文联合确认。
4. **回查局部受影响的内容。** 记录证据时间与来源。无变化时更新下一次回查时刻，有变化时重算受影响决策的候选集合。完成或过期的任务退出监控。候选收益、预算和最晚有用时刻共同确定唤醒时刻。操作与通知由同一个下游执行器处理，各实验组共用其行为规则。

第一版实装时优先做手标依赖的上限诊断，再用冻结 LLM 提取依赖并测损失。分数可从开发集可解释的离散风险表开始。决策价值里若已纳入变化概率、时延和后果，直接使用净值。原案 `影响 × 风险 × 紧迫度 / 成本` 可作为基线，避免把这些因素在同一策略中估计两次。

原型 `direction_b_demo.py` 枚举一条读取的来源和启动时刻。它比较最大单个决策收益和去重后的联合决策收益，用同一个掌握真实依赖的终止决策规则评估两组。共享依赖时联合选择航班状态，净收益增量为 2.20，单任务策略选择场地查询，为 1.80。三条决策的边际变化概率与截止不变，接送改成独立后两策略都选择场地，净收益均为 1.80。规划器误把独立接送当成依赖时，联合策略降至 1.00。数字来自手工概率和效用。它们说明为何要做配对和依赖失配实验。循环回查、订阅与语言模型均未在该原型中运行。

暂定论文问题是 *Which Evidence Should a Personal Agent Refresh Next?*。可支持论文主张的完整链条包括可复现的原生漏读或读晚、及时补证后同一执行器恢复、以及相同资源下依赖调度在独立任务上改善表现。

## 验证顺序和停止条件

- **第一关，原生 SentinelBench。** 先重放可见条件、需要进入详情、No-op 三类。固定模型、上下文、工具权限和评分。逐条标记真正的漏看或读晚，并用同一时刻的可见证据回放做恢复诊断。详情见 [实验协议](sentinelbench.md)。
- **第二关，依赖是否有用。** 案例覆盖同源复用、跨页面或跨来源竞争、近截止、无共用依赖和依赖错标。配对时保持事件密度及观测成本。用任务级配对统计报告同预算及时成功率、额外核验和误操作。若原生任务没有足够的多待定决策，同分布组合任务按扩展协议报告。
- **第三关，长期验证。** 通过前两关后，验证 VibeLifeBench 的持续任务是否有足够的可修复观测失分。先跑原生交互，再按需要扩展公共时钟。ProEvent 原生是给定消息和当前日程后预测操作，可用于观察后的状态维护补充检验。端到端观察预算需要具备独立的信息获取接口。 [VibeLifeBench 论文](https://arxiv.org/html/2608.10875) · [ProEvent 任务定义](https://github.com/GZ-Li/ProEvent#task)

若原生失分主要来自已经看到证据后的推理和执行，优先重新评估问题设定。若手标依赖也无法改善与强基线的质量、成本及延迟权衡，暂停扩展全量长期任务。若只在手标依赖有收益，判断提取错误和依赖歧义是否是主要瓶颈。
