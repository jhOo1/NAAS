# SentinelBench 首轮验证

## 原生任务能测到什么

官方提供 10 个模拟应用，每个 10 个场景。运行器用任务提示和起始网页启动 agent 子进程，维护模拟时间与事件，再用任务自带规则评分。公开结果字段包含 `success`、`condition_at` 和 `contact_get_time`。任务是否支持跨页面观察，与其是否存在多个相互竞争的开放任务，是两个需要分别核验的问题。 [论文 §2–3](https://arxiv.org/html/2606.05342#S2) · [官方运行器说明](https://github.com/microsoft/sentinel_environments#3-eval-harness)

| 首轮切片 | 原生样例 | 要验证的失分 |
| --- | --- | --- |
| 当前页可见 | `micromail-unread-absolute-passive`，等待未读邮件达指定数量 | 是否能正确注册条件、保持监控、按时报告 |
| 证据藏在详情 | `micromail-body-december-relative-active`，检查邮件正文是否也提及十二月 | 列表事件出现后，是否打开正确候选并获得可决策证据 |
| 需要进入不同会话且无目标事件 | 附录 C 的 MicroChat 文件附件 No-op | 是否把列表层变化误报成附件，是否过早结束 |

以上为论文与公开文档审查。首轮实际轨迹、官方分数复现、全量依赖覆盖率均未验证。原生双决策切片需要查阅任务契约和可见交互，样例的复杂操作或同页多个对象本身无法证明存在多任务预算竞争。 [完整原生任务列表](https://arxiv.org/html/2606.05342#A3)

## 主对照与成本

- **原论文 `sleep` 和 `wait_for`。** 论文的 `wait_for` 用自然语言条件阻塞，比较页面文本快照，去重差分，调整刷新与 LLM 调用间隔，超时时强制复查。用公开附录的伪代码复现时标注重实现，并计入内部快照、刷新、模型调用和时间。 [论文附录 D](https://arxiv.org/html/2606.05342#A4)
- **同工具强基线。** 给对照同样的候选来源、跨页面导航、缓存、计时器和 `wait_for`，由冻结 LLM 选择轮询、切换或注册等待。再比较最近截止优先、周期轮询、独立的单任务价值排序。用同样的去重，使联合价值的效果可以与缓存、预置规则和工具能力区分。
- **方法消融。** 关闭跨任务依赖，留单任务分数。用固定时间替代自适应回查，留同样的依赖。用出处与活动条件已手标的版本测调度上限，再切到模型提取。无预算上限只作资源曲线参照。

先用公开单任务入口做三类开发重放。冻结后在 held-out 场景配对，同一场景各臂共用事件时钟、`speed_factor`、模型和执行器。运行中的 agent 只见任务提示、正常交互的页面和公共时钟。场景脚本、评分查询和真实条件时刻专供运行器与离线归因。一个外部工具调用可能包含很多次内部检查，比较时同时记录工具调用次数、检查数、页面刷新、模型 token 与有效延迟。 [运行入口与计时字段](https://github.com/microsoft/sentinel_environments#runtime-tuning)

## 失败归因和判定

固定当时历史和执行器，比较原本观察、同时间点补给真实可得的关键证据、同成本无关证据三组。先区分漏看或读晚、读到但语义误判、已经正确判断但执行或提交失败。区分页面导航延迟和有效条件出现后的响应延迟。

主要比较在共同预算上限下的**限时成功率**。报告多个期限下的成功曲线，将漏检保留在分母里。同时报告官方成功率、成功样本的官方 Reaction Time、No-op 正确率和过早/错误操作率。源差异、语言提取错误和 API 失败独立计数。配对统计以场景为单位，开发切片与留出确认单列。

如果原生切片只支持检验同页与导航核验，先报告这项原生诊断。跨任务依赖的主要比较使用等成本的共享/拆分依赖对，要求相同可见时钟、事件密度、语义执行器和预算。组合多个原生场景时，主表标注扩展协议，官方原始分数另报。
