# PM-Bench v9 九次读取择时对照

2026-11-19。固定上游 `e1093c470c8981daf522d4ef047a7c3a71e077d7` 的官方 `synthetic_week_v9`，原生一周共 80 个事件步。两组使用相同 Qwen3.5-27B API、原生动作菜单、通道策略、执行器和 9 次环境读取。 [官方基准](https://github.com/genglinliu/PMBench/tree/e1093c470c8981daf522d4ef047a7c3a71e077d7)

## 两组唯一区别

预先把公开的一周总步数均匀切成 9 个不重叠的事件步区间，每段分配一次读取。固定周期在区间中点读取，具体为第 `5、13、22、31、40、49、58、67、76` 步。按需组在区间内第一个建议立即读取的事件执行；若直到末步都没有建议则末步必读。这是以原生事件步计的周期，两组各用 9 次。段末约束用于在相同资源消耗下检验段内择时，预算不能跨段结转。

每个事件步向同一模型发送对应轨迹的原生可见历史、菜单和相同提示，输出临时 `choose`、一个读取通道和是否建议立即读取。两组都直接使用该通道建议，固定组只忽略是否立即读取的字段。需要读的事件步使用官方 `query_state` 解析器生成该通道的原生返回，并由相同动作提示和执行器重新做 `choose`。其余事件步执行临时 `choose`。两组不接触隐藏时间、隐藏事件、官方标注或对方的轨迹。无效动作只走空待办的退化路径，避开原生模型运行器使用到期待办作为失败回退的分支。

每组 80 次共同提示调用加 9 次同模板读后动作调用。两组以事件步交错请求，使用相同模型参数及按步配对的 seed。早期选择会改变同组后续菜单、历史及通道建议，这些是择时干预的闭环后果。比较只覆盖一个公开合成周，方案不等价于官方虚拟分钟心跳或不同读取预算的已发布跑分。

## 证据和计分

- 保存逐步模型原始输出、原生状态回包、实际交给模型的显示文本、最终动作、当前到期待办、缺项和额外动作。对于隐藏条件，按到期同一步的通道、事件 ID 和状态返回核对。`clock` 还核对返回时间是否等于该步时钟。这个指标度量当前明确回包，先前历史推断与未见证据猜中另计。
- 用原生 `score_log` 统计周 Set-F1、全部和须监测待办的准时命中、迟到、漏做和误报。另报有待办到期的步骤中完成全部的比例，以及无额外动作的完整匹配。保留 API 报告的输入输出 token、调用数和出错／重试记录。
- 独立的官方回放校验逐项比较存下的原生回包、模型可见文本、到期待办和每日 TP/FP/FN。只有两组都完成全部 80 步并通过 9 次读取审计后，才报告正式对照分数。

## 复现

```sh
python3 run_pmbench_timing.py /path/to/PMBench \
  --api-utils /path/to/distill/utils.py --output runs/pmbench-timing-20261119.json
python3 run_pmbench_timing.py /path/to/PMBench \
  --verify-only --output runs/pmbench-timing-20261119.json
```

如果输出已存在且调用中途停止，用同一路径加 `--resume` 保留已经成功的模型返回。验证模式不请求模型也不改写结果。
